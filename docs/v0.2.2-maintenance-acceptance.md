# v0.2.2 maintenance-chain acceptance — frozen before implementation

Status: **implementation/test scope only**. Production installation, release,
candidate gray observation and fleet deployment remain disabled.

This stage is accepted only when the same maintenance implementation provides
backup, exact stop, fresh install, v0.2.1-style upgrade, failed-start rollback,
explicit rollback and uninstall/archive behavior without process-name or command-
line-substring termination.

## Identity and stop contract

- Resolve the Scheduled Task by exact task name/path and export its XML before
  mutation. Parse its action with Windows command-line rules.
- A launcher is owned only when its executable path and complete parsed action
  arguments match the task. A runtime is owned only when its executable path,
  parsed `-File`/`-ConfigPath` values and parent launcher identity all match.
- Capture PID, UTC creation file time, executable path and parent before stop.
  Revalidate all fields immediately before any forced termination. Never kill by
  image name, basename, wildcard, substring or an unrefreshed PID.
- Stop the exact task and allow a bounded graceful exit. If the old launcher or
  v0.2.1 residual runtime remains, terminate only the previously captured exact
  process identity/tree. Verify every captured identity has exited within ten
  seconds. Ambiguous or unverifiable identity fails closed.
- An unrelated decoy process with a similar command line or script basename must
  remain alive throughout isolated tests.

## Backup contract

Before file/task mutation, create a host-local unique backup directory containing:

- exported task XML and its SHA-256;
- the complete existing install directory;
- bridge configuration, state, action ledger, health/process receipts and Codex
  config when present;
- original presence/absence, hashes and canonical destination for every item;
- pre-stop process identities, task state, host/user/time and a machine-readable
  receipt/manifest.

Quiesce the exact bridge before copying mutable files. Verify every backup copy
against its recorded hash. A partial backup cannot authorize installation.

## Install/upgrade contract

- Verify a bounded manifest and every candidate artifact before loading candidate
  code or stopping the task. Reject missing, extra, unsafe-name or hash-mismatched
  files. Production mode requires an accepted clean artifact and deployment gate;
  development artifacts are allowed only under an explicitly bounded test root,
  unique test task name and isolated paths.
- Stage and verify all files before an atomic same-volume directory swap. Preserve
  machine-specific bridge configuration and policy; a package never supplies or
  overwrites another host's configuration.
- Preserve existing task principal/triggers/settings by modifying only its exact
  action. A fresh install creates the documented bounded default task.
- Readiness requires one exact launcher/runtime pair, current creation identities,
  matching process receipt, live health, package version and installed manifest
  hashes. A degraded or uncertain bridge is not ready.
- Any post-backup failure automatically attempts rollback and returns both the
  original failure and rollback result. It must never report installation success
  merely because files were copied.

## Rollback contract

- Verify the backup manifest before mutation, stop the current exact task/process
  set, restore the install directory by staged swap, restore bridge-owned state,
  and restore/remove the original task exactly from exported XML.
- Preserve external edits outside the bridge-owned Codex config markers while
  restoring the backed-up managed block. Refuse to overwrite a concurrently
  modified bridge configuration rather than silently discarding user changes.
- Restore original file absence as well as file content. If the original task was
  running, start it and verify the exact original process pair; otherwise leave it
  stopped/absent. Record a rollback receipt and backup location.

## Isolated maintenance test matrix

All tests use a unique directory below ignored `.artifacts`, a unique temporary
task name beginning `Codex-Worktree-Trust-Bridge-Test-`, isolated config/state/
Codex config and controlled runtimes. They may not stop or change the production
task, installed bridge or business processes.

Required cases:

1. Fresh install and explicit uninstall/archive.
2. Upgrade from a controlled v0.2.1-style launcher/runtime that demonstrates a
   residual child after task stop; exact cleanup must remove it while retaining a
   decoy process.
3. Successful candidate startup with preserved config, task settings and one
   launcher/runtime pair.
4. Explicit rollback to exact original files/task/config/state and running state.
5. Candidate manifest corruption rejected before stop/mutation.
6. Candidate startup failure automatically rolls back to the original version.
7. Duplicate/ambiguous owned process identity fails closed without broad kills.
8. Concurrent bridge-config edit causes rollback conflict rather than overwrite;
   external Codex-config content outside managed markers survives rollback.
9. Runtime/launcher crash and ordinary task stop leave no owned process tree.
10. Positive and negative status/readiness results use live identities and hashes.

Each case has a finite deadline, raw logs, hashes and cleanup receipt. The final
test must prove the production task/version/PID/creation identities and hashes are
unchanged. No recurring task, delayed background validation or release tag may be
created by this stage.
