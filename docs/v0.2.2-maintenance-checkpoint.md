## Implemented maintenance behavior

### Exact process identity

Maintenance resolves one exact Scheduled Task action, parses the complete Windows
command line and captures PID, UTC creation file time, executable path and parent
relationship. A launcher must match the action executable and all three action
arguments. A runtime must match its expected PowerShell executable, `-File`,
`-ConfigPath` and parent launcher. Identity is revalidated immediately before any
forced termination.

No image-name, basename, wildcard or command-line-substring process termination is
used. Ambiguous launcher/runtime identity fails closed. An unrelated PowerShell
process running a same-basename script remained alive in every maintenance case.
Already-exited transient descendants may disappear during read-only observation;
the exact launcher and main runtime remain strict identities.

### Backup and install

Candidate file names, complete file set and hashes are verified before task stop.
The quiesced host-local backup records task XML/hash, pre-stop process identities,
the complete install directory, bridge config/state/action ledger, health/startup
receipts and the Codex managed block. Backup payload hashes and the backup-receipt
hash are bound into the installation receipt.

Installation uses a same-volume staged directory swap. Existing task principal,
triggers and settings are preserved while only the action is changed. Existing
machine policy and unknown config fields are retained; only `packageVersion` is
advanced. The expected post-install config hash is frozen before startup, so a
concurrent edit cannot be silently adopted as the installation result.

Readiness requires one exact launcher/runtime pair, process-birth identities,
startup receipt paths and hashes, live health, allowed UI state and an exact
installed manifest/file set. A stale, degraded, resource-unhealthy or uncertain
runtime is not ready.

### Rollback and uninstall

Explicit rollback verifies the bound backup receipt before mutation, refuses to
overwrite a bridge configuration changed after installation, restores the
complete previous install and exact task XML, and restores the original running
or stopped/absent task state. The backed-up managed Codex block is merged into the
current file so unrelated later edits survive.

Candidate startup failure automatically invokes the same rollback. Uninstall
creates and verifies a backup first; injected failures after task or install
removal automatically restore the original installation. Successful uninstall
retains its backup and machine-readable receipt.
